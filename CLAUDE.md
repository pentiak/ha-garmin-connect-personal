# ha-garmin-connect-personal

Home Assistant custom integration `garmin_connect_personal`, released through HACS, written to
core's rules for a later core submission (ADR-0004).

Start with the Status section of `docs/PLAN.md`. `docs/DESIGN.md` describes how it works,
`docs/DECISIONS.md` why. `custom_components/garmin_connect_personal/quality_scale.yaml` is the
checklist of quality-scale rules; update it whenever a rule's state changes.

## Commands

```shell
.venv/bin/pytest                                  # 95% coverage gate (rule test-coverage)
.venv/bin/mypy                                    # strict, integration code and script/ only
.venv/bin/ruff check . && .venv/bin/ruff format --check .
.venv/bin/python -I script/gen_translations.py    # after every strings.json change
.venv/bin/pre-commit run --all-files              # detect-secrets, ruff, mypy, zizmor
.venv/bin/zizmor --offline .                      # GitHub Actions security lint
```

Fresh clone: `python3 -m venv .venv`, then `.venv/bin/pip install -e ../aio-garmin-personal`
first, then `.venv/bin/pip install -r requirements_test.txt`, then
`.venv/bin/pre-commit install`. The editable install satisfies the library pin, so this works
before that version is on PyPI, and library changes are picked up without a release. Every
pre-commit hook runs a tool from `.venv`; none is downloaded.

## Guardrails

- **Ruff** uses Home Assistant core's configuration, copied into `pyproject.toml` and
  `tests/ruff.toml` (ADR-0018). Do not loosen it here; a rule core enforces would only fail
  later at the core submission. Re-copy both when core changes them.
- **No `from __future__ import annotations`.** Core bans it; Python 3.14 defers annotations.
- **Docstrings** on every function, tests included, as core requires.
- **Workflows** pin every action to a full commit SHA with the version as a comment, chosen at
  least seven days after its release, except hassfest and the HACS action, which are
  published on a branch only (ADR-0019). `.github/zizmor.yml` holds that exception.
  `actions/checkout` always gets `persist-credentials: false`; workflows start from
  `permissions: {}` and grant per job.
- **Security scans** (`security.yml`): gitleaks, Trivy, zizmor on every push, PR and weekly;
  CodeQL once the repository is public (ADR-0020). `.gitleaks.toml` skips
  `.secrets.baseline`, and must keep the single `[allowlist]` table that gitleaks 8.24 reads.
- **`.secrets.baseline`** lists the fake keys in the tests and the `api_key` labels in the
  strings. When detect-secrets flags something new, confirm it is not a real secret, then run
  `.venv/bin/detect-secrets scan --baseline .secrets.baseline --exclude-files '^\.venv/'`.
- **Dependabot** proposes action and pip updates weekly. It updates
  `requirements_test.txt` but not `manifest.json`; a library bump needs both by hand.

## Releases

A release PR sets `version` in `manifest.json` and moves the `CHANGELOG.md` entries under a
`## X.Y.Z - YYYY-MM-DD` heading. After it merges, the maintainer tags the merge commit `vX.Y.Z`
on `master`; `release.yml` checks the tag against the manifest and creates the GitHub release
from that changelog section (ADR-0024). Add each user-visible change to `## Unreleased` in the
PR that makes it.

## Traps

- **Translations.** `strings.json` is the source; `translations/en.json` is generated by
  `script/gen_translations.py` and committed. A custom integration loads `en.json` as is, so an
  unresolved `[%key:…%]` shows up literally in the UI. CI fails if the generated file is stale.
- **Schemas** use `probatio`, not `voluptuous`. HA 2026.10's flow types expect `probatio`, and a
  voluptuous schema fails strict mypy (ADR-0013).
- **Device lookups in tests** use `device_registry.async_get_device_by_identifier(identifier,
  entry_id)`. The old `async_get_device(identifiers=…)` raises in the test harness.
- **mypy** covers `custom_components` and `script` only, as core does; the test harness ships
  without type information.
- **The library dependency** is pinned in `manifest.json` (`requirements`) and in
  `requirements_test.txt`. Change both, together with the library release. CI installs from
  PyPI, so it fails until the pinned version is published.
- **The test harness pin** (`pytest-homeassistant-custom-component`) fixes the Home Assistant
  version tested. When raising it, including in a Dependabot PR, raise `homeassistant` in
  `hacs.json` to match.
- **Day boundaries** come from the Garmin profile time zone, not Home Assistant's (ADR-0006).
  Tests in `test_init.py` set Home Assistant to `Pacific/Auckland` to catch a mix-up.

## Code style

Follow core: `typing.override` on overridden methods, `ConfigEntry.runtime_data`, entity
descriptions with `value_fn`, translated names, errors and icons, `PARALLEL_UPDATES` in every
platform. When unsure how core does something, read a current Platinum cloud-polling integration
in `.venv/lib/python3.15/site-packages/homeassistant/components/`. `google_health` is the
closest match: health data, calorie and step sensors.
